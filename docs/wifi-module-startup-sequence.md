# MakeSkyBlue Wi-Fi 模块启动时序与被动监听开发指南

本文给出足够的信息，使开发者无需依赖本仓库固件，也能实现一个严格
RX-only 的双向 UART/Modbus 监听器。所有协议结论来自 2026-08-08 对官方
Wi-Fi 模块热插拔的实测；一次观测到的等待时间不是协议常量，实现不得依赖
固定延迟。

## 1. 硬件与安全边界

| 监听端 | AtomS3 | 信号方向 | 角色 |
| --- | --- | --- | --- |
| G1 | GPIO1 RX | Wi-Fi 模块 → 逆变器 | Modbus 请求及启动标记 |
| G2 | GPIO2 RX | 逆变器 → Wi-Fi 模块 | Modbus 响应 |

- 串口配置为 9600 baud、8 data bits、no parity、1 stop bit。
- GPIO1/GPIO2 均为浮空输入：关闭内部 pull-up 和 pull-down。
- 监听器必须与通信双方共地，只接收已确认的 3.3 V TTL。
- 不得配置 `tx_pin`，不得调用 UART write，也不得实例化会主动轮询的
  Modbus controller。监听器不能向任一通信方发送任何字节。
- 不要把 5 V TTL、RS232 或 RS485 A/B 直接连接到 AtomS3 GPIO。

两个方向必须使用独立 UART RX 和独立重组缓冲区。全局采集序号可以共用，
但它只是监听器生成的 `uint32_t` chunk 序号，不是 Modbus transaction ID。

### 1.1 Modbus 通信地址与 D 地址

Modbus RTU 帧的第一个字节是从站通信地址。本设备的所有已验证请求/响应首字节
均为 `0x01`，所以当前逆变器通信地址是 1。`D11`、`D30` 等是寄存器地址，
不是设备通信地址；例如 `01 06 00 0B ...` 中 `01` 是通信地址，`000B` 才是
D11。

被动监听器不需要预设或主动扫描通信地址。它从每个 CRC 正确的 G1 请求首字节
读取地址，再要求对应 G2 响应使用同一地址。合法单播地址为 1–247；0 只允许
写广播且不会等待响应；248–255 为保留值并标为结构错误。这样可在完全不向总线
写入的前提下自动取得地址。如果换一台设备，应先保留原始帧，再以多组请求和
响应的一致首字节确认地址，不能只看一个噪声字节下结论。

HA 中的 `Last Modbus Communication Address`、`Observed Modbus Communication
Address Count` 和 `Observed Modbus Communication Addresses` 都直接来自上述
合法帧。本机连续抓包只出现地址 1。一个本地预览表曾把 D18 称为 communication
address，但实际 D18 在同一窗口始终为 0，因此不能假设 D18 就等于线上的地址，
也不能擅自套用 `D18 + 1`；在受控修改或官方编码证据出现前，D18 保持 raw。

## 3. 启动阶段的原始数据

### 3.1 D30-D31 网络时间同步

第一次观测到的 G1 请求：

```text
01 10 00 1E 00 02 04 0A 10 DB C5 EB 91
```

字段解释：

| 字节 | 值 | 含义 |
| --- | --- | --- |
| slave | `01` | 设备地址 1 |
| function | `10` | FC16/0x10 Write Multiple Registers |
| start | `00 1E` | D30 |
| count | `00 02` | D30-D31，共两个 word |
| byte count | `04` | 四个数据字节 |
| data | `0A 10 DB C5` | 32 位打包时间 |
| CRC | `EB 91` | Modbus CRC16，低字节在前 |

对应 G2 确认：

```text
01 10 00 1E 00 02 21 CE
```

确认帧必须回显 slave、function、start 和 count；仅按 function 配对会在丢帧
后产生错配。

### 3.2 可选的 `000000FF` 启动标记

第一次热插拔窗口内，G1 单独出现：

```text
00 00 00 FF
```

它没有 Modbus 地址、功能码或 CRC，因此不能作为损坏的 Modbus 帧处理。第二次
热插拔没有出现该标记，所以不得等待它或用它判定启动成功。当前
实现将其分类为 `wifi_module_startup_marker` 并保留原始序号。识别必须先于
Modbus 帧长判断，并支持跨 chunk 分片：

```text
如果 G1 缓冲区是 00 / 0000 / 000000：继续等待最多四字节
如果前四字节是 000000FF：记录启动标记并消费四字节
否则：进入普通 Modbus RTU 重组
```

这一规则只应用于 G1。不要因为看见一个 `00` 就立即丢弃，否则标记会被误报
成 unknown bytes，并在后续合法帧到来时进一步产生假 CRC 错误。

### 3.3 恢复后的常规轮询

本设备随后循环读取四段 holding registers：

| 请求 | 地址范围 | word 数 |
| --- | --- | ---: |
| `01 03 00 00 00 3D 84 1B` | D0-D60 | 61 |
| `01 03 00 64 00 33 44 00` | D100-D150 | 51 |
| `01 03 00 C9 00 10 94 38` | D201-D216 | 16 |
| `01 03 00 97 00 32 75 F3` | D151-D200 | 50 |

响应长度为 `5 + byte_count`，其中最后两字节为 CRC。响应可能被 UART callback
拆成多个 chunk；只有收齐完整长度并通过 CRC 后才能解析寄存器。

### 3.4 实测 FC06 D11 单寄存器事务

连续抓包在 `2026-08-08 14:59:24+08:00` 首次观测到 Wi-Fi 模块下发：

```text
G1 request:  01 06 00 0B 03 34 F9 2F
G2 response: 01 06 00 0B 00 00 F8 08
```

请求字段为 slave 1、FC06、D11、写入值 `0x0334=820`。请求前 FC03 读到
D11=800，紧接着的 FC03 读回 D11=820，证明这次请求已经反映到设备状态。
17 分钟后又观测到：

```text
G1 request:  01 06 00 0A 02 6C A8 85
G2 response: 01 06 00 0A 00 00 A9 C8
```

这次请求 D10=`0x026C=620`，但请求前后 FC03 都读到 D10=600，所以不能认为
它已经生效。两次响应都保留了 slave、function 和 D 地址，但最后一个 word
都是 `0x0000`，并没有按标准
Modbus FC06 回显请求值。因此本项目把它明确记录为独立的
`write_response_value_u16`，目前不进一步猜测 `0` 的业务含义。

在 `2026-08-08 17:37:02+08:00`，操作者又把 IoTRix/面板所称的 **d13**
输入为 70。总线上没有出现 Modbus D13 写请求，而是出现：

```text
#24848 G1 request:  01 06 00 0A 02 BC A9 19
#24849 G2 response: 01 06 00 0A 00 00 A9 C8
#24850 G1 read:     01 03 00 00 00 3D 84 1B
#24851 G2 readback: FC03 D0-D60 response
```

请求实际是 Modbus D10=`0x02BC=700`，即 70.0 A；设备专用响应值仍为 0。
紧随其后的 #24851 中 Modbus D10 仍为 600（60.0 A），所以这次请求也没有得到
读回确认。同一帧中的 **Modbus D13 仍为 70**，按其独立的 `/10` 规则显示为
7.0 kW。这个受控变化同时证明：IoTRix/面板小写 d13 映射到 Modbus D10，绝不能
因为编号相同就把它解释为大写 Modbus D13。

配对条件为同一 boot 内一秒内到达、slave/function/D 地址相同；请求值和响应值
分别保存，不能因两者不同而丢掉这个真实事务，也不能把响应值伪装成标准回显。
是否实际应用必须再记录该地址的首个 FC03 读回值；`0000` 既不能单独证明成功，
也不能单独证明失败。

## 4. D30-D31 32 位时间格式

D30 是高 word，D31 是低 word，按 big-endian word 顺序组合：

```text
packed = (D30 << 16) | D31
```

位域：

| 位 | 宽度 | 解释 |
| --- | ---: | --- |
| 31..26 | 6 | year offset，年份 = 2024 + value |
| 25..22 | 4 | month |
| 21..17 | 5 | day |
| 16..12 | 5 | hour |
| 11..6 | 6 | minute |
| 5..0 | 6 | second |

解码公式：

```text
year   = 2024 + ((packed >> 26) & 0x3F)
month  =          (packed >> 22) & 0x0F
day    =          (packed >> 17) & 0x1F
hour   =          (packed >> 12) & 0x1F
minute =          (packed >>  6) & 0x3F
second =           packed        & 0x3F
```

实测 `0x0A10D951` 解码为 `2026-08-08 13:37:17`，对应抓包时间
`13:37:18`。实现仍应验证 month/day/hour/minute/second 的合法范围，不应盲信
总线数据。

### 4.1 Modbus D 地址与面板 d 参数不是同一编号体系

大写 `Dxxx` 表示 Modbus 请求中的实际 register address，必须保留在 HA 名称和
CSV 中。不要把它与 LCD/IoTRix 设置页的小写 `dxx` 参数号混为一谈。`5-6KW
Hybrid Solar Inverter User Manual 0331` 第 21 页把面板 d11/d12 定义为最低电池
电压和启动放电电压，并把 d13/d14 定义为电网/PV 充电电流；第 22 页的面板 d18
才是最大交流输出电流。本机 IoTRix 2.2.31 设置值与同刻 UART 则证明这些设置
分别落在 Modbus D8、D9、D10、D11 和 D12。尤其 Modbus D11=820 按 0.1 A
缩放为 82.0 A，Modbus D12=300 缩放为 30.0 A；两者均已在 CSV 标为
`confirmed_semantic`。因此，名称里即使都出现“D11/D12”，也必须同时注明是
`Modbus D` 还是面板 `d`，不能凭编号直接互换。

上面的 d13=70 受控操作又独立复现了这条映射：线上的 FC06 地址是 Modbus
D10、raw 是 700，而 Modbus D13 保持 raw 70。大小写和命名空间不是排版约定，
而是避免把 70.0 A 写操作误判为 7.0 kW 寄存器写操作的协议边界。

## 5. 推荐的流式解析算法

1. 系统启动后立即初始化两路 RX，并在 Wi-Fi/API 之前开始收包。
2. 每次 callback 先生成递增 `uint32_t` 序号，再把 source、uptime、长度和原始
   bytes 放入 ring buffer。
3. G1/G2 分别追加到自己的 stream buffer，不能按 callback 边界当作帧边界。
4. G1 先检查 `000000FF` 启动标记前缀。
5. 按方向和 function 推导长度；变长读响应使用 `5 + byte_count`。
6. 验证 Modbus CRC16。CRC字节序为 low byte、high byte。
7. G1 完整请求进入 pending queue；G2 响应按下列条件寻找请求：
   - slave 与 function 相同，异常响应忽略 function 的 0x80 位；
   - FC01/02/03/04/17 校验响应 byte_count；
   - FC05/08/16 校验完整 PDU 回显；
   - FC06 按本设备实测行为校验 D 地址相同，并分别保留请求值与响应值；
   - FC0F/10 校验 start 与 count 回显。
8. pending request 超过一秒仍无响应时单独记为 expired，不允许以后同长度响应
   与它静默错配。
9. 所有原始记录都先保存；未知数据只能增加诊断计数，不能覆盖或隐藏原始值。

监听器只观察写请求。看到 FC05/06/0F/10/16/17 不代表监听器执行了写入。

## 6. Ring buffer、CSV 与 Home Assistant

建议每条 ring record 至少包含：

```text
record_type, source, gpio, sequence, uptime_ms, byte_count,
hex, overwritten_total, buffer_remaining, message
```

启动时应先插入一条 `BOOT` onboarding record，使 HA 重连后仍能知道监听器的
启动次序和 ring 容量。`uint32_t sequence` 从上电开始增长；判断连续性时需要
考虑 `0xFFFFFFFF → 0` 回绕。

本项目向 HA 暴露：

- `D30-D31 observed_network_time`；
- `D30 network_time_high_word` 与 `D31 network_time_low_word`；
- `Wi-Fi Module Startup Markers`；
- CRC、discarded、unknown、pending、expired、unpaired 和 ring overwrite；
- 每个已读地址的 `Dxxx` 命名字段或显式 `Dxxx raw_register`。

HA event/CSV 是网络传输链路，不应被当成硬实时 UART 边界。需要法证级无丢失
时，应增加本地非易失存储或独立逻辑分析仪。

## 7. 独立实现验收清单

- [ ] 生成代码中 GPIO1/GPIO2 只有 INPUT，pull-up/pull-down 都关闭。
- [ ] 配置和生成代码中不存在 TX pin、UART write 或主动 Modbus controller。
- [ ] 分片请求和分片响应都能重组，chunk 边界不影响结果。
- [ ] 如果出现 `000000FF`，计入可选启动标记且不增加 CRC/unknown/discarded；
      如果不出现，仍能解析 FC16/0x10 + FC03 链，但不把周期校时误报为重启。
- [ ] D30-D31 的 FC10 请求与 G2 ACK 严格配对。
- [ ] 四组 FC03 轮询总计覆盖 178 个 word。
- [ ] 序号缺口、ring overwrite、CRC、unknown、expired、unpaired 都有独立指标。
- [ ] HA 断线期间继续收包；重连后能看到 onboarding 和 ring backlog。
- [ ] 连续 24 小时报告保留每次异常的原始十六进制和序号范围。
