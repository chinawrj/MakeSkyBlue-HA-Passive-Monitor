# MakeSkyBlue 独立通信主体：未来设计与完整支持边界

本文是切换准备文件，不是启用 TX 的授权。当前已发布配置仍是严格 RX-only：
GPIO1/GPIO2 都是浮空输入，没有 `tx_pin`，也没有 UART write。只有在原 Wi-Fi
模块已经物理移除、接线复核完成、单独的 direct-role YAML 已发布并通过审计后，
AtomS3 才能从监听器变成主动通信模块。

**2026-09-07 文档基线：本次不实施切换、不刷写、不重启、不发包。** 以下把
“将来可以由 AtomS3 独立承担通信”作为架构假设，而不是已经验证的设备能力。
本文涵盖完整生命周期；未证实的协议条件必须显式保留，不能用一个猜测的
“完整初始化序列”替代实验。原模块启动的逐帧事实见
[启动证据](wifi-module-startup-sequence.md)，当前运行方法见
[monitor 文档](atoms3-g1-g2-modbus-monitor.md)。

术语：**已观测**是本项目抓包/UI 支持的事实；**设计要求**是未来实现必须满足
的约束；**待验证**表示不能用于上线承诺。本文中的超时、退避、控制策略若没有
明确样本来源，均为设计要求，不是逆变器协议常量。

## 1. 项目和角色命名

角色中立的项目族名称使用 **MakeSkyBlue Local Link**。两个角色必须始终显示在
文件名、HA 设备信息和日志中：

| 角色 | 建议名称 | 总线能力 | 当前状态 |
| --- | --- | --- | --- |
| `passive_monitor_rx_only` | Passive Monitor | G1/G2 仅接收 | 已实现、默认 |
| `direct_mode_preview` | Direct Mode Preview | G1/G2 仍仅接收 | 已实现、无 TX |
| `direct_readonly_bridge` | Direct Read-Only Bridge | 经验证的请求脚 TX，另一脚 RX；仅 FC03 | 尚未实现 |
| `direct_control_bridge` | Direct Control Bridge | 单一主体；额外按白名单允许校时/控制 | 仅设计，尚未实现 |

这里的 “Read-Only Bridge” 表示不写逆变器寄存器。它仍必须在物理线路上发送
FC03 读请求，所以绝不能和“电气 RX-only”混为一谈。

### 1.1 当前 preview 的 HA 配置

alpha.6 提供 `PREVIEW Arm Direct Mode Permanently` 开关。它是单向锁存：开启后
HA 不能关闭；只有整片擦除偏好存储才可清除。开关开启不会立即生效，两个 RX
输入必须连续 30 秒没有任何字节，状态才从
`armed_waiting_for_30s_uart_idle` 进入 `preview_ready_no_tx_compiled`。

方向也不靠固定 G1/G2 假设：固件同时监听两脚，至少配对四组 CRC 正确的
FC03/FC04 请求和响应，才把请求所在脚保存为未来 TX candidate、响应所在脚保存
为未来 RX。HA 会显示 `Detected Future TX Pin`、`Detected Future RX Pin`、配对数
和冲突票数。

preview ready 仍不等于主动通信。该固件没有 `tx_pin` 和发送 API，所以无论开关、
idle 或方向状态如何都不能输出 UART。只有操作者明确确认原 Wi-Fi 模块已物理拔除
后，后续独立 release 才可加入实际 direct role。

`preview_ready` 是历史预演锁存值，不是现场接线证明、方向有效性证明或永久 TX
许可。30 秒静默不能证明原模块已移除，更不能证明其 TX 已处于高阻态。原模块
拔除后若总线静默，监听器不能凭空重新学习方向；未来实现必须校验先前留存的
方向证据和物理接线，缺失、矛盾、设备更换或接线变更时一律停在不发送状态。

仓库现有名称保留被动监听阶段的证据血缘。角色中立入口是
`makeskyblue-local-link.yaml`；目前它只能 include
`makeskyblue-modbus-monitor.yaml`。未来的主动角色必须使用新的独立文件，例如
`makeskyblue-direct-readonly.yaml`，不能向当前 monitor YAML 塞入一个容易误开的
`tx_pin` 开关。

## 2. 为什么不用一个布尔 TX 开关

ESPHome substitutions 只是文本替换，不能作为可靠的硬件安全边界。如果同一份
YAML 同时包含 RX 和 TX 路径，即使默认关闭，也可能因本地 substitution、package
合并或重构而意外启用。因此采用两个独立的顶层配置：

```yaml
# 当前 makeskyblue-local-link.yaml
packages:
  selected_role: !include makeskyblue-modbus-monitor.yaml
```

未来切换必须是一次可审计的源码变更、commit 和 prerelease；不得仅在未跟踪的
secrets 文件里偷偷切换。CI 要分别检查生成的 `main.cpp`：

- passive role 必须恰好有 GPIO1/GPIO2 两个 `set_rx_pin`，且没有 `set_tx_pin`、
  `uart_write`、`write_array` 或 `.write(`；
- direct role 必须只有经接线证据确认的请求脚 TX 和响应脚 RX（本机样本是
  G1 TX/G2 RX），且构建与现场启用分别需要明确确认；
- 两个角色的固件文件名、项目版本和 SHA-256 必须不同。

## 3. 当前接线事实和未来引脚角色

当前实测为 3.3 V TTL、9600 baud、8 data bits、no parity、1 stop bit，并与
AtomS3 共地：

| 线路 | 被动模式 | 原模块移除后的候选角色 |
| --- | --- | --- |
| G1 / GPIO1 | RX，观察 Wi-Fi → inverter | TX，AtomS3 → inverter RX |
| G2 / GPIO2 | RX，观察 inverter → Wi-Fi | RX，inverter TX → AtomS3 |

G1 变成 TX 前必须逐项满足：

1. 原 Wi-Fi 模块已从 TX/RX 线路物理拔除，不能只在软件中停用；
2. 断电状态下复核 G1 确实通往逆变器 RX，G2 确实来自逆变器 TX；
3. 上电后复核高电平不超过 3.3 V，不接 5 V TTL、RS232 或 RS485 A/B；
4. 共地可靠，线路上不存在第二个发送器；
5. 先使用限流/串联保护和示波器或逻辑分析仪确认波形；
6. 主动固件必须来自已经发布且 CI 通过的 tag。

任何一项不成立，就继续使用 passive role。

## 4. 已收集的原 Wi-Fi 模块行为

所有结论来自本项目 clean-room 双向抓包。Modbus RTU 地址是帧首字节，当前所有
结构正确的请求/响应均使用地址 `1`。D 地址是寄存器地址，不是通信地址。

### 4.1 固定读轮询

Wi-Fi 模块按下列顺序循环发送 FC03：

| 顺序 | 请求 hex | 地址范围 | word 数 |
| ---: | --- | --- | ---: |
| 1 | `01 03 00 00 00 3D 84 1B` | D0–D60 | 61 |
| 2 | `01 03 00 64 00 33 44 00` | D100–D150 | 51 |
| 3 | `01 03 00 C9 00 10 94 38` | D201–D216 | 16 |
| 4 | `01 03 00 97 00 32 75 F3` | D151–D200 | 50 |

在一段 21 分钟样本中，每个范围约读取 178–179 次。正常完整轮询周期中位数约
3.08 秒；同一轮相邻请求的间隔通常约 0.3–0.9 秒。观察到的最长 UART 静默约
30.4 秒，因此替代模块不能把单次 30 秒空档直接判成设备掉线。

响应完成延迟的样本中位数约为：D0 段 158 ms、D100 段 132 ms、D201 段
60 ms、D151 段 134 ms。首版 direct role 应使用明确超时、有限次数重试和整轮
退避，不能在超时后高速重发。

### 4.2 原模块的写事务

抓包还观察到：

- FC10 写 D30–D31，用于同步打包网络时间；通常三次一组，约每五分钟重复；
- 设备特有的 FC06 写 D10/D11，响应并不按标准 FC06 回显请求值。
- FC06 写 D36 的强制充电计划 bit 0，已有一次开启操作及读回证据。

这些写事务必须继续保留为协议证据，但 **direct_readonly_bridge 首版全部禁用**。
首版只发送上述四个 FC03 请求，不发送 FC06、FC10 或广播，也不提供 HA 写服务。
不做 D30–D31 校时能否在逆变器冷启动后直接读取，**尚未验证**；只读首版以此
作为待测假设，不能在失败时自动升级为写入初始化。如果以后确需校时或控制，必须另做受控实验、
独立许可开关、独立 release 和读回验证。

#### 4.2.1 已观测写入的线类型与证据边界

Modbus RTU 帧中的 register address 和 register value 都按高字节在前传输；每个
register 在设备数据模型中仍是一个 16-bit word。工程单位、是否有符号、比例和
是否允许写入是四个不同问题，不能仅凭 `UINT16` 猜测可写性。

| Modbus D 地址 | 已观测功能码 | 线上存储/编码 | 工程值 | 当前证据 |
| --- | --- | --- | --- | --- |
| D10 | FC06 request | 单个 big-endian `uint16` word | `A = raw / 10`；反向编码候选为 `raw = round(A * 10)` | 两次观测到请求 `raw=620`、`raw=700`，后续 FC03 都仍读到 600；后者来自 IoTRix/面板 d13=70，写入生效 **未确认** |
| D11 | FC06 request | 单个 big-endian `uint16` word | `A = raw / 10`；实测 820 = 82.0 A | 请求前 800、请求 820、随后 FC03 读回 820；本次写入生效已确认 |
| D12 | 未观测到写请求 | FC03 读取为单个 `uint16` word | `A = raw / 10`；实测 300 = 30.0 A | 只确认读语义；**不能声称可写，也不能声称使用 FC06** |
| D30–D31 | FC10 request | 两个 big-endian `uint16` words，先 D30 高 word、再 D31 低 word，组合为 packed `uint32` | year/month/day/hour/minute/second 位域 | 多次抓到原模块写入和设备 ACK；首版 direct role 不发送 |
| D36 | FC06 request | 单个 `uint16` word；已观测请求 1、响应 0、读回 1 | bit 0 强制充电计划开启 | 只确认一次 0→1；关闭、其他位、组合值和安全写策略待验证，禁止整字猜写 |

D30–D31 的位域公式和完整原始帧见
[启动协议](wifi-module-startup-sequence.md)。本表只描述已经从 clean-room 抓包验证的
线格式，不构成对任何地址的通用写入许可。未来若加入一个可写字段，必须同时保存
请求 raw、响应 raw、紧随其后的 FC03 读回、IoTRix/面板同刻值和失败回滚条件。
公开的 `direct_readonly_bridge` 首版不会包含任何上述反向编码函数或 HA 写实体。
IoTRix/面板小写 d13=70 的线事务实际落在 Modbus D10=700；同一读回中的
Modbus D13=70 表示 7.0 kW。未来实现必须把这两个命名空间作为不同字段处理。

### 4.3 启动行为

多次重启观测表明，原模块联网后会发送 D30–D31 时间同步，然后恢复四段 FC03
轮询。一次出现过无 CRC 的 `00 00 00 FF`，其他重启没有出现，所以它只是可选
标记，不是握手必需条件。完整时间线和打包时间格式见
[启动协议](wifi-module-startup-sequence.md)。

未来设计不等待该 magic，也不实现原厂云端登录。目标是在网络未连接时即可
启动本地 FC03 轮询，并将结果保存在本地缓存；但“未联网/未校时的冷启动能否
成功”仍需独立台架验证。Wi-Fi、WireGuard 和 HA 仅负责上报，不应成为 UART
调度的依赖。本项目没有覆盖原厂云账号、配网或远程升级协议，不能称为云模块的
逐功能兼容替代品。

## 5. direct role 的最小状态机

以下是下一阶段的实现约束，不是当前固件行为：

1. 初始化经确认的响应脚 RX、解析器、请求队列和本地缓存；
2. 只有通过物理切换确认的 direct 固件才初始化经确认的请求脚 TX；
3. 依次发送四个 FC03 请求，每次等待地址/function/byte-count/CRC 都匹配的响应；
4. 更新与当前被动解析器相同的 D0–D216 缓存和 HA sensors；
5. 超时记录 raw 请求、等待上下文和计数，有限重试后退避；
6. Wi-Fi/HA 断线时继续本地轮询并缓存诊断；
7. 不实现 FC06、FC10、线圈写、广播或任意透传写接口。

主动请求也需要一个独立的 `uint32` transaction sequence；它不能替代捕获 chunk
sequence。日志必须同时保存发送 hex、接收 hex、时间、地址、功能码、请求序号、
响应配对和超时结果。

## 6. 切换前必须保留的数据

在拔除原 Wi-Fi 模块前，至少保存：

- 一个完整正常轮询窗口，覆盖全部 178 个 D 地址；
- 至少一次由操作者明确记录时刻的 Wi-Fi 模块重启；
- FC03 四段请求的周期、顺序、响应延迟和超时分布；
- 所有 FC06/FC10 原始 hex、方向、时间、sequence、响应及后续 FC03 读回；
- UART 静默区间、CRC/discarded/residual、sequence gap 和 log reorder；
- 同刻 IoTRix UI 只读快照，用于确认字段而不是复制 APK 资源；
- 当前 passive firmware 自报版本、配置 SHA、固件 SHA（如已留存）和 boot ID。

若旧固件二进制没有留存，报告必须写 `missing/not preserved`，不能拿当前工作区
里尚未刷入的二进制哈希冒充设备固件。

## 7. 切换执行清单

1. 停止并封存最后一条 pre-cutover 日志，生成 JSON 摘要和 SHA-256；
2. 记录逆变器、Wi-Fi 模块、AtomS3 的供电状态和接线照片；
3. 整机断电，物理拔除原 Wi-Fi 模块；
4. 万用表/示波器复核 G1/G2 方向、电压和共地；
5. 发布 direct-role prerelease，等待 CI 和生成代码 TX/RX 审计通过；
6. 首次上电只运行 FC03，观察首个请求和响应后再允许后续轮询；
7. 比对被动阶段基线、HA sensors 和逆变器面板，不写任何设置；
8. 从该 direct-role 固件上线时刻重新开始独立 24 小时窗口；
9. 每 30 分钟检查在线、序号、CRC、超时、heap、缓冲区和 178 地址覆盖。

如果 direct role 不能稳定取得响应，应断电回滚接线或刷回 passive 固件；不得通过
发送探测写命令来猜协议。

上述清单仅用于未来另行授权的切换窗口，不在当前设备执行。回滚时必须先停止
主动输出并断电隔离；不得先接回原模块、再尝试让主动固件停止发送。

## 8. 完整初始化生命周期（未来实现规格）

原模块的**已观测顺序**是“暂停轮询 → 一次或多次 FC10 校时/ACK → FC03 四段
轮询”，其间可能有可选标记，后续校时可穿插轮询。它没有证明校时是读取的
前置条件，也没有覆盖逆变器冷启动、首次配对、恢复出厂和全部故障状态。
因此把原模块证据与替代主体的初始化分开：

| 阶段 | 输入与动作（未来设计） | 成功出口 | 失败/未证实时 |
| --- | --- | --- | --- |
| S0 安全启动 | 加载角色、发布版本、接线证据与站号；TX 保持未启用 | 唯一主体与配置均确认 | 保持 RX-only 安全停机，不探测脚位/波特率/站号 |
| S1 接收准备 | 先建立 RX、分帧缓冲、单事务队列、单调时钟、错误计数与新 boot ID | 队列为空、内存可用、旧事务无效化 | 不启用 TX |
| S2 总线占用确认 | 复核原模块物理隔离；观察线路仅作为附加诊断 | 操作者确认且无竞争发送迹象 | 禁止发送；静默计时本身不放行 |
| S3 首次读 | 只读角色启用已确认 TX，发送 D0–D60 FC03；只留一个待响应事务 | 同站号/功能码/122 数据字节/CRC 正确 | 有限重试与退避；不补发校时或 magic |
| S4 基线读取 | 依次 D100–D150、D201–D216、D151–D200 | 四段完整、178 word 均有新鲜读值 | 部分值标记缺失/过期，禁止以零填补 |
| S5 周期运行 | 公平执行四段读；独立更新本地缓存与 HA 发布 | 每个地址保留 raw、状态、时间与版本 | 单段异常不抹去其他段；严重链路异常进恢复态 |
| S6 可选校时/控制 | 仅另行发布的控制角色，在独立许可和白名单下执行 | ACK 与后续读回形成业务结果 | 结果未知时停止控制，不无限重试 |
| S7 重连/复位恢复 | 清理过期事务、建立新基线；HA 重连仅重新发布状态 | UART 独立恢复、数据新鲜 | 不重放断线期间积压的设置命令 |

这张表是待实现契约，不表示仓库已有可执行 direct driver。

### 8.1 启动组合与断电语义

独立台架需逐项验证：逆变器先启动、主体先启动、同时冷启动、仅主体重启、
仅逆变器重启、逆变器睡眠/故障、无网络、时间无效、HA 离线、残留半帧启动。
每种组合都须记录首次响应、四段就绪时间、异常与停止条件；原模块热重启样本
不能替代这些组合。不得假定已缓存的旧传感器值就是本次启动的成功证据。

持久化只保留经过校验的角色/站号/方向映射及其证据版本。待处理请求、未确认写入、
旧的 `preview_ready` 不可作为复位后的发送许可；接线证据失效时重新人工确认。
启动及故障时不能输出未经定义的字节。看门狗重启不得使写命令再次执行。

## 9. 事务调度、异常与恢复

以下针对未来主体；不要把当前被动解析器的一秒配对窗口当成已证实的设备超时。

| 项目 | 设计约束 / 必测场景 |
| --- | --- |
| 帧边界 | 独立保存 RX 字节流；按长度、CRC、合法站号和当前请求验证；驱动 callback 不是帧边界。当前 8 ms 分块设置不是线上协议常量 |
| 读响应尺寸 | 四段数据 byte count 分别为 122、102、32、100，完整 RTU 响应为 127、107、37、105 字节；不能用 96 字节 chunk 上限截帧 |
| 请求配对 | RTU 没有 transaction ID；一个在途请求，校验站号/功能码/byte count；FC03 响应无 start，不能仅凭同长度判定请求归属 |
| 超时与迟到响应 | 从请求发送完成计时；分别记录首字节与完整响应延迟。超时后隔离迟到/残余数据并留恢复静默窗口，不立即发同形请求，否则无法可靠区分旧响应 |
| 节流 | 以第 4.1 节约 3.08 秒周期为观测基线；显式配置帧间间隔、完整响应超时、最大重试次数与退避上限，台架定值后才发布；禁止零间隔忙重试 |
| 校验失败 | CRC、结构错误、unsupported function、discarded、residual 独立计数；保留完整上下文，不用 CRC 偶合片段更新寄存器 |
| 异常响应 | 保留功能码的 `0x80` 异常位与异常码；未知码原样记录。已知永久性非法功能/地址/值不盲重试；临时忙/不可用仅按已验证策略退避 |
| 非请求响应 | unpaired 与 expired 分开；来自其他站号的帧不能更新本站缓存，也不触发扫描/广播 |
| 竞争主体 | 发现额外请求、方向冲突或无法解释的持续活动时停止调度并告警；软件观察不能替代物理单主体隔离 |
| 资源不足 | 有界队列/缓冲；RX 溢出或无法保留诊断时暂停控制并进入故障态；显示 heap、最大连续块和丢弃原因，不能因 HA 背压阻塞 RX |
| 读值质量 | 每段附采样时间、boot、请求号、valid/stale/unknown 状态；两个 word 的值只在同一完整响应内组合；禁止将四段不同时间读值宣传成原子快照 |

在重试次数和隔离时间尚未经过台架确定前，该规格不得被视作可直接上电的参数表。

## 10. 校时、控制及其他支持矩阵

未来完整产品可分层扩展，但“独立工作”不等于“所有 D 地址可写”。运行许可必须
分成主体接管、校时、每类设置控制三个层次；只读主体永不隐式调用后两层。

| 能力 | 本项目证据 / 当前支持 | 未来主体政策与缺口 |
| --- | --- | --- |
| 四段 FC03 遥测 | 已观测；被动解析与内存 poll planner 已实现 | 只读首版唯一请求白名单；冷启动独立读取待验证 |
| FC04 | 被动解析器可解码 | 没有本机轮询用途证据，主体不发送 |
| D30–D31 校时 | FC10 packed time 和 ACK 已观测 | 控制角色独立许可；不是只读角色初始化步骤 |
| D11 充电电流 | FC06 800→820 有读回证据 | 范围、步进、设备条件、拒绝行为仍需验证后才能开放设置 |
| D10 电网充电电流 | 请求 620/700 后读回仍 600 | 保持不可控；响应 word 0 不是成功，禁止声称已支持设置 |
| D36 充电计划开关 | 开启 bit 0 有一次读回证据 | 关闭及其他位未知；禁止整字写入或猜测读改写能安全保留其他位 |
| D12 与其他 confirmed 读字段 | 仅有读语义不构成写证据 | 默认没有写实体；每项须独立验证 |
| 18 provisional / 93 raw 地址 | 有 raw 观测、语义尚未完备 | 保留原值和证据状态；不能导出控制接口或猜单位 |
| 计划时间、强制放电、工作模式、复位 | 部分读字段/相关性不等于完整控制协议 | 默认禁用；逐项补请求、响应、读回、运行条件和风险边界 |
| 广播、线圈、任意透传、地址扫描 | 不是本机已证明需要的初始化 | 不提供；解析器识别某帧不代表主体支持发送 |
| 原厂配网/账号/云服务/远程升级 | UART 启动样本未覆盖 | 不实现、不模拟；项目目标是本地 HA 接入，不承诺原厂云兼容 |
| 新型号/站号/波特率 | 目前样本只有本站设备配置 | 先 RX-only 建立独立兼容性证据，不自动扫描或套用本机配置 |

### 10.1 时间服务的完整边界

编码依据仅为[已观测 D30–D31 位域](wifi-module-startup-sequence.md#4-d30-d31-32-位时间格式)：
年份表示范围 2024–2087，月份/日期（含闰年）、时分秒均须合法。编码不含时区；
现有样本与当地墙钟对应，但不能据此认定设备使用 UTC 或具备夏令时支持。未来
配置必须明确设备本地时区，拒绝无效/未同步时钟、越界年份和未经许可的大幅跳时。

约五分钟一次、三次一组只是原模块样本，不是必须复刻的协议约束。控制角色需
验证校时间隔、掉网时的本地时钟策略、跨日/跨年、时钟回拨以及对充放电计划的
影响，再决定是否启用。FC10 ACK 仅确认该事务响应；记录后续读回和时间差，
不能要求不断走动的时钟 raw 值与请求逐位永久相等。无时间源时继续只读遥测，
标记时间质量，不写零值或编造当前时间。

### 10.2 设置事务与不确定结果

未来每个写白名单项须包含：准确 D 地址、功能码、编码/舍入规则、合法范围、
步进、可写前提、未知位策略、预期响应、读回验证、超时处理和安全恢复方式。
先取得新鲜基线；序列为“明确操作意图 → 条件校验 → 单次发送 → 响应分类 →
首次及必要后续 FC03 读回 → applied/rejected/unknown”。FC06 响应值 0 必须
独立保存，不解释成通用成功码。校验不一致就标为未确认，不伪造成功状态。

响应丢失时写入可能已经生效，不自动重复写、不在重连/重启后重放 HA 队列。
只有证明操作可安全重试才允许有限重试。所谓“回滚”也可能是第二次危险写入；
没有独立验证的恢复方式就停止控制并请求人工检查，不能自动恢复旧值。

## 11. 本地独立运行与 HA 接口契约

未来主体的 UART 调度不依赖 HA、VPN、云服务或网络校时成功。HA 只订阅状态；
断网后的缓存、采样时间和 stale 标志要与已持久化的历史分开。重连发布当前状态
和诊断，不伪造断网期间完整历史。设置接口若以后提供，必须鉴权、限定白名单、
防重复意图，并在通信/数据过期时拒绝操作；不得开放任意 hex 服务。

每笔事务记录 role、firmware/config/git 标识、boot ID、独立 transaction sequence、
TX/RX 原始 hex、设备单调时间、墙钟及其质量、chunk 序号范围、配对结果、异常码、
重试与读回结论。TX 表示未来主体自身发送；monitor 当前捕获的 G1 是原模块发送，
不能在历史报告中改记成 AtomS3 TX。按 boot 区分 u32 回绕、重启、重复与真正缺号。

当前 HA append/ACK 路径有[已知阻断](atoms3-g1-g2-modbus-monitor.md#known-capture-blocker-2026-09-07)。
未来实现必须有真实 payload 的端到端测试：数据落盘后才 ACK，允许同 key 相同
payload 重放，但拒绝冲突重复；覆盖、ACK 失败、断电丢 RAM 都必须显式报告。
不能把 entity Last UART Chunk 的历史快照当作完整事务日志。
